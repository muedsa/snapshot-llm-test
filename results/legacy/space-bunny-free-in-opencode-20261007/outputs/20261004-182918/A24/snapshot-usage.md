## 1. 排程结论（全部由程序算出，见 `schedule.json` / `schedule-audit.json`）

模型按 TASK.md 原文实现：`design`/`engineering` 各只有一个团队，同团队不可并行、不可抢占；
`tasks[].teams` 是**可选集合**（R05/R09/R12 列为两项，各只占用其中一条通道）；必须跑满输入时长；
先决任务完成后才能开始（在前置结束的那一分钟起算为合法）；切换团队无耗时；未缩短任何时长、
未删除 R10/R11 两个检查环节、未调整任何输入时间。

| 量 | 值 | 出处 |
|---|---|---|
| 总工作量 | **485 分** | 12 个 `minutes` 求和 |
| 忽略资源的关键路径 | **255 分** R01→R04→R07→R09→R10→R12 | DAG 最长链（自由排程） |
| 工作量/两团队下界 | **⌈485÷2⌉ = 243 分** | 每队每分钟最多做 1 分工作 |
| 组合下界 | **max(255, 243) = 255 分** | 两者不可同时满足 |
| 本方案 makespan | **260 分 → 13:20** | 穷举搜索最优解 |
| 距 16:00 剩余缓冲 | **160 分** | 420 − 260 |
| design / engineering 负载 | 255 分 / 230 分 | 两队各自零重叠 |
| 内部空档 | 各 5 分 | design 10:25–10:30 等 R05；engineering 12:20–12:25 等 R09 |

**最优性是可核验的，不是"我觉得最好"**：`plan.py` 对全部合法（任务顺序 × 选定团队）排程做了穷举
DFS（访问 1570 个节点，0.01 s），最小 makespan = 260；再用独立的随机化 schedule-generation 搜索
（20 万次，seed=20261107）复核，同样没找到更早方案。选定方案还经过一次从零开始的独立校验
（团队资格 / 精确时长 / 窗口 / 每条依赖 / 每对同队区间重叠），结果 0 问题。
`plan.py` 里带 `raise SystemExit` 的断言：若随机搜索优于穷举结果则直接报错退出，避免把不完整的搜索
说成穷举。另外写入了 **255 分下界不可达**的证明（`schedule-audit.json` →
`lower_bounds.why_the_lower_bound_is_not_attainable`）：若 255 分可行，关键路径必须零间隙从 0 跑完，
R07 就必须在 85 分开始，因而 R05 必须在 85 分前完成；而 135 分前 engineering 需承载
R02+R03+R06+R05=135 分工作且 R02→R03→R06 不可打断，只能把 R05 排到 105–135，矛盾。
因此 `260 分最优` 是有证明的，而 `255 分` 只作为下界呈现，三张图都写明「关键路径·无资源」。

## 4. 本题踩到的 DSL 语义坑（都是真实响应）

| 现象 | 定位方式 | 修复方式 | 复验 |
|---|---|---|---|
| `400 PARSE_ERROR: Attr [gradientColors] unsupported CSS color [['#101836FF'] ...]` | 首次渲染，看 `responses/resp-A24-req-001-*.txt` | 参考 A01 已有用法，`gradientColors` 必须是逗号分隔字符串、`gradientBegin/End` 取 `CENTER_LEFT/CENTER_RIGHT` | 后续渲染 200 |
| `400 PARSE_ERROR: Attr [border] value is invalid`（`border="#FFFFFF1F"`） | 第 2 次渲染 req-002 | border 必须是 `"<宽> SOLID <色>"`；`theme.bd()` 统一补全 | 200 |
| 块内 6–7 字中文标签被**静默丢弃**（`D.warnings()` 报 "needs ~2 line(s) but box holds 1"） | 第 4 版看图 + warnings | 所有单行 Text 都先量宽（`est_width`），块内标签/时长/前置按实测宽度决定画不画；窄块只保留编号+时长 | 第 5 版起 warnings=0 |
| 泳道上方标注互相压字：任务名行与时刻行用了各自的错行位，落到同一 y | 第 5 版看图 | 改成两条**互不重叠的固定色带**（任务名 2 行 + 时刻 2 行），行内再用贪心首适配错行 | 第 7 版确认无压字 |
| 块内 `决定链` 文字与 `前置 R04·R05` 重叠 | 第 5 版看图 | 块内不再放决定链文字，改为洋红描边 + 底部索引标注；块右上角加 6px 圆点 | 复验无重叠 |
| 依赖索引 6 行与图例行相撞（10 行分 2 列不够） | 第 6 版看图 | 改 3 列 × 4 行，图例/脚注整体下移 | 复验无重叠 |
| `400 PARSE_ERROR: minHeight must be between 0 and maxHeight ... height="-13.5"` | 简报第 2 次渲染 req-013 | DAG 走线时同层通道内多条边按 `len(pairs)` 均分通道（原来按通道高度算导致第 3 条落到目标行下方） | req-014 起 200 |
| `400 RENDER_ERROR: renderBox.parentData must be StackParentData` | 行动卡第 1 次渲染 req-020 | `theme.chip()` 原来把 `Positioned` 当子节点塞进 `Container`，改成同层两个 `Positioned` 兄弟 | 200 |
| 全角空格 U+3000 行首缩进被 Inter 渲染成 0 宽 | 简报缩进放大截图 | 改成用 x 偏移表达悬挂缩进（U+3000 在行首时落到 Inter 而非 CJK 回退） | 1.6× 放大复验缩进正常 |
| `est_width` 对等宽字体偏小（DejaVu Sans Mono 步进 0.602em vs 估计 0.55em），时刻被截断 | 第 1 版看板看图 | 新增 `theme.mw()`：等宽文本按 `est*1.12+16` 给宽 | 第 2 版起完整显示 |

另有两处**不是 DSL 坑、但必须如实记录的过程 bug**（都发生在本地脚本，未污染交付图）：
① 排程搜索最初把「已完成任务的结束时刻」存在全局数组里做下界剪枝，导致剪枝不健全并输出了
一条违反依赖的排程（R12 早于 R10）；改为沿当前路径维护 `FIN[]` 后，穷举结果与随机交叉验证一致为 260。
② 反向推演的 `LF` 误用 `max` 应为 `min`，以及资源无关最晚开始时间的循环方向反了（正序导致读到的
后继仍是 0）；两处修正后 `resource_delay` 才有意义（R05/R07/R09/R10/R12 各 +5 分）。
