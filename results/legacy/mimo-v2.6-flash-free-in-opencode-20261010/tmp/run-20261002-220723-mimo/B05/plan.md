## 一、现实中值得解决的问题

**老旧多层住宅（无电梯）的加装电梯协商。**

四条卡点，全部是"信息与共识"问题，而不是技术问题：

1. **意愿不齐**——同一单元里，高楼层强烈需要，低楼层担心采光、噪音、通行与房价，
   无人牵头就永远停在"再说吧"。
2. **费用分摊众口难调**——同一笔 28.8 万元自付，按楼层摊、按面积摊、还是让 1–2 层
   免摊，同一户在不同方案下可以差出两万多元。这是最真实的分歧点。
3. **信息不透明**——造价 52.8 万由哪些项构成、补贴能抵多少、工期多久、报价哪家可信，
   居民没有共同的事实底座，只能靠传言。
4. **牵头人精力有限**——业委会/楼组长靠 Excel + 微信群 + 纸质表推进，谁答应了、谁还没谈、
   谁的顾虑没销项，没有可追踪的载体。

**产品要让"一栋楼的加装电梯"变成一张所有人都看得懂的图。**

## 二、产品定义

| 项 | 内容 |
|---|---|
| 名称 | **同梯 TongTi**（"同梯"= 同一部电梯，也谐音"同意"） |
| 一句话 | 把一栋楼的"装不装、怎么分、什么时候装"变成一张看得懂的楼栋剖面图 |
| 形态 | 居民端（微信小程序/手机 Web）+ 牵头人/居委会端（桌面 Web），**本任务只做静态画面，不实现前端** |
| 受众 | 老旧小区居民（含高龄）、业委会/楼组长、社区居委会、施工与电梯供应商 |
| 产品机制 | 楼栋唯一码 → 剖面意愿图 → 分摊模型试算 → 顾虑台账 → 方案比选 → 签约公示 → 施工 → 验收 → 十年总账 |
| 关键设计决策 | **以"楼栋剖面"作为贯穿全产品的主数据结构与主视觉母题**：一户一格、颜色即态度、高度即楼层、引出线即费用 |
| 虚构信息 | 楼栋"梧桐里小区 3 号楼"、人物、造价、补贴、报价、维保价格均为**演示数据**，画面与元数据标 DEMO |

### 不做什么（边界）

- 不声称真实部署、不引用未取得的政策条文、不做真实用户验证（未做，不声称做过）。
- 不做登录页、不做营销落地页（TASK 明确不预设）。
- 不做运行程序，全部为静态画面。

## 三、贯穿全产品的一致样例数据（跨画面必须一致）

**楼栋：梧桐里小区 3 号楼 · 一梯两户 · 6 层 · 12 户 · 总建筑面积 931.8 ㎡**

| 层 | 西户 | 面积 | 东户 | 面积 |
|---|---|---|---|---|
| 6 | 601 | 76.4 | 602 | 78.9 |
| 5 | 501 | 76.4 | 502 | 78.9 |
| 4 | 401 | 76.4 | 402 | 78.9 |
| 3 | 301 | 76.4 | 302 | 78.9 |
| 2 | 201 | 76.4 | 202 | 78.9 |
| 1 | 101 | 76.4 | 102 | 78.9 |

- **意愿**：已签约 7 · 已同意待签约 2 · 有顾虑待沟通 3（101 / 202 / 602）→ 支持率 9/12 = 75%
- **造价（演示）**：甲方案 52.8 万元；补贴演示 24.0 万元；**自付 28.8 万元**
- **工期（演示）**：65 天；当前施工第 28 天 → 43.1%
- **分摊权重（模型 A，以顶层为 1.00）**：1F 0.00 · 2F 0.30 · 3F 0.50 · 4F 0.70 · 5F 0.85 · 6F 1.00
  权重和 = 2 × (0+0.3+0.5+0.7+0.85+1.0) = **6.70**
  单位权重 = 288,000 ÷ 6.70 = **42,985.07 元**
- **三种模型的每户自付（元，四舍五入到元）**

| 模型 | 1F 西/东 | 2F | 3F | 4F | 5F | 6F | 合计 |
|---|---|---|---|---|---|---|---|
| A 按楼层递增（1F 不出钱） | 0 / 0 | 12,896 | 21,493 | 30,090 | 36,537 | 42,985 | ≈288,002¹ |
| B 按建筑面积均摊 | 23,614 / 24,386 | 同左 | 同左 | 同左 | 同左 | 同左 | 288,000 |
| C 低层免摊（1F、2F 都不出） | 0 / 0 | 0 | 23,607 | 33,049 | 40,131 | 47,213 | 288,000 |

¹ 分项四舍五入到元导致 ±2 元差异，合计以 288,000 元为准（画面注明）。

- **同户跨模型极差**：最大 **24,386 元**，**102 室与 202 室并列**
  （均为 B 24,386 − C 0；次高为 201/101 的 23,614 元，601 为 23,599 元，602 为 22,827 元）
- **低层零负担户数**：A 2 户 / B 0 户 / C 4 户
- **年度公共支出（演示）**：维保 4,800 + 电费 1,800 + 年检保险 1,200 + 大修准备金 6,000 = **13,800 元/年**
- **十年账**：初始 288,000 + 运行 138,000 = **全楼 426,000 元**；每户年均 3,550 元
  - 602 室十年总额：A **63,582** · B **36,071** · C **69,836**（极差 33,765 元）
    - A = 42,985 + 138,000÷6.70 = 42,985 + 20,597
    - B = 24,386 + 138,000÷931.8×78.9 = 24,386 + 11,685

## 五、技术路线

- **DSL 由 PowerShell 生成器产出**（复用 B03/B04 的 `TBlock`/`Card`/`HR`/`VR` 等 helper 与
  文本越界 Fit 守卫），每件是完整自包含的 `<Snapshot>` 根文档，根标签不写宽高。
- **零外部素材**：剖面图、堆叠条、柱线图、时间轴、清单、勾选框、滑块全部用矩形/圆/文本手绘；
  现场"照片"用 DSL 画的示意缩略并标注 `示意图 DEMO`，不冒充真实照片。
- **服务**：`POST https://open-snapshot.muedsa.com/snapshot`，全字段写 `requests.jsonl`。
- **看图**：逐张 `read`；遇到内容哈希串图则用 `System.Drawing` 改 1 个角像素生成唯一字节副本后再读，
  识别靠画内烘焙的报头 + 画幅比例。
- **计算**：`calc-b05.ps1` 用脚本算出全部分摊/造价/十年数字并写 `calc-b05.json`，
  DSL 生成器只从该文件读数，**不在 DSL 里手抄算式**。

因此本产品：

- **不引用任何政策条款、补贴标准、法定同意比例**；
- 造价、补贴、报价、维保、电费**全部标注 `演示数据 DEMO` / `以当地政策核定为准`**；
- 补贴 24.0 万元在画面与 `product-brief.md` 中同时写明**尚未完成外部政策核验**；
- 分摊权重、模型规则是**产品自定义的规则**（可解释、可复算），不冒充法规要求。

文档抓取另发 **10 条 `type=documentation`**（ai-guide + 9 个 DSL 文档 + `/fonts`），全部 200。

## 七、完成标准（逐张自查）

1. 每张 `final.png` 字节 = 该次成功响应的 `bytes`；IHDR 尺寸 = DSL 首个 `Container` 宽高。
2. 用看图工具实际打开；文字可读、无重叠、无越界、无截断、对齐成线。
3. 跨画面数字一致（面积、造价、自付、工期、签约数、天数）。
4. 装饰不能被误读为按钮；有状态的画面必须有反馈（06 含错误态 + 成功态）。
5. 每张画幅比例互不重复；每张的使用者、设备、需求、结果不同。
6. `iterations.jsonl` 记录 baseline + 每轮视觉迭代（observation / view_evidence）。
7. 未做真实用户验证 → 不声称做过，写入 `product-brief.md` 验证边界。
