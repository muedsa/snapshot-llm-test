## 6. 设计选择、经验与未解决事项

关键设计选择（每一处都有预览/看图依据）：

- **底色与三色**：深空 `#080D1C` 统一整套手册，强调只用 ember（日/危险）、cyan（几何/月食）、corona（日冕/高亮），纸面 `#EFE6D3` 只给件-02（“账本”要读起来像印刷纸）。看图依据：件-02 v01 的主标题完全没显示——`header()` 少传 `paper=True`，纸上浅色压在纸底上等于隐形；补上后纸本配色才成立。
- **版式随内容变**：几何页要有锥（件-01 扫描线）、清点页要能数（件-02 点阵）、时间轴按真实天数比例（件-04）、档案页保留等宽原文（件-05）、点图保持面积比（件-08）。十件骨架不同但页眉编号与脚注数据带一致。
- **把差异留在图上而不是抹平**：件-05 的两个 ΔT、件-07 的两种算法、件-08 的整数度量化、件-06 的“最宽不等于最长”，都在版面上并列，让读者看到不一致本身。
- **看图会推翻设计而不是只调字号**：件-01 的 ② 区原本画“放大扫描锥”，v03 的 2× 裁图看出扫描线露出明显条带、远地点那行的尖端翻到月球左侧，v04 直接把锥体删掉换成从 0 出发的余量条＋三角记号（轴量的是尖端相对地表的差距，月球并不在该轴的固定位置——语义错误，不是画得不够好）。
- **跨件呼应靠图内标记**：件-08 v03/v04 加的十字标记指回件-05、件-07 逐点分析过的 2024-04-08 与2027-08-02 两次食甚点；图例文字从“十字 05/07”（读者无法解码的套件内部编号）改成“2024/2027”。
- **件-10 用元页面收束**：与其写一段“编者感想”，不如把关系、分级、来源账与限制做成可核对的表；矩阵的 15 条边来自“两个生成器实际读同一个 research/*.json”，不是编辑感觉。

可复用的经验（Snapshot 相关）：

- 提交前的本地自检比服务报错便宜：TextFit（SLACK 0.96／PITCH 1.45，CJK 1.0 em、空格 0.30 em、拉丁数字 0.50 em）把“文字压盖/被截”类问题在发请求前拦下，本题 0 次 400 就是这么来的；被拦下的行一律拆行或换词，不缩字号硬塞。
- 密集版面必须靠 2× 裁图判断：9.5 px 的 URL 清单在整图预览里“看起来没问题”，裁图才看出被切底（件-10 v03→v05）。
- `Container color=` 画矩阵格子时，0 值格要与底衬同色系否则网格消失（件-10 v03→v04 加 `#05080F` 底衬）。
- `Transform matrix=` 是唯一可靠的斜线手段，但小角度下 1 px 线的抗锯齿会闪断；刻度密度要跟着降。
- 服务无 path 图元：任何曲线/圆锥都提前设计成“矩形扫描线 + 圆角”可接受的形态，并在图上注明棱角限制。
- 长渲染（>2 min）用后台任务等完成，不要重发：件-10 v07 那次截断正是等待期，重发前先看 Content-Length 与实际字节。
- 自指型页面（件-10）要预留“快照时刻”语义：所有统计标明截至点、本件自己在表外，交付后差值写进 case.md。

未解决事项与限制（均为已如实呈现，不是待补工作量）：

- 件-02、件-03 的 case.md 与成品 DSL 未以路径形式点名任何来源文件（早期只写“见 sources/ 目录”），件-01 仅 1 处；件-10 的 C 区如实标为缺口并用 D 区整份列出 25 个去重页面补救，未回头改写那两份报告（改写会让“当时的记录”失真）
