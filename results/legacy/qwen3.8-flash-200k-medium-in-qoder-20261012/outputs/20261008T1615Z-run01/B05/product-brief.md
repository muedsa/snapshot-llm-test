# 枝安 · 产品简报（B05 件-01 至 件-10）

> 品牌、示范城市「汀州市」、街道名、树种名录、工单号、台风名与全部数字均为**虚构演示**。
> 数据由 `tmp/<run>/B05/b05data.py`（固定种子 20261011）生成，10 件共用同一份
> `research/stats.json`，任何一件里的数字都能由脚本复算。**未做真实用户验证**，
> 本文所有"用户会……"的表述都是待验证假设，不是研究结论。

## 1. 问题

城市行道树的管理链条上，每个环节都有人在看树，但没有一个环节能回答"这棵树现在该谁管"：

| 环节 | 现状 | 断点 |
| --- | --- | --- |
| 市民发现歪树 | 打 12345 或发业主群 | 报完不知道是哪棵、有没有人去看 |
| 巡检 | 纸质台账 + 微信群照片 | 上次谁看过、看过之后有没有下文，查不到 |
| 隐患判定 | 巡检员个人经验（倾斜、空洞、根系、下方有没有人） | 换个人换个结论，无法排序 |
| 台风前处置 | 按路段喊话 | "先加固哪 100 棵"给不出可解释的依据 |
| 雨后统计 | 层层电话上报 | 数字到上级手里已混入未核实项，且没人去重 |
| 年度汇报 | 宣传语 + 自定指标 | 覆盖率口径经不起追问 |

## 2. 方案

一个统一的风险分把六个角色的工作面串起来：

```
R = 0.30·S_倾斜 + 0.25·S_空洞 + 0.20·S_根系 + 0.15·S_暴露对象 + 0.10·S_历史病害
R≥70 立即处置 ／ 55–69 限期处置 ／ 40–54 观察期 ／ <40 正常
```

权重与阈值是**产品自定口径**（本文第 5 节说明它缺什么证据）。关键是：十张图里出现的
每一次"红/橙/黄/绿"都来自这同一个分数，市民报修页的等级和值班大屏的等级不会互相打架。

角色 × 介质 × 状态，各出一张图，构成 10 件作品：

| 件 | 谁在什么环境下用 | 要完成的事 | 画面 |
| --- | --- | --- | --- |
| 01 | 市民，人行道上一手遮阳一手操作 | 定位到具体那棵树、补齐必要字段、提交前确认 | 1080×2340 手机，未提交态 |
| 02 | 巡检员，户外强光、戴手套、单手持 | 读实测值与判级依据 | 1080×2400 手持机，现场态 |
| 03 | 值班调度，3 米外看 2560×1440 | 风险在哪、今天谁做什么、哪单超时 | 大屏，实时态 |
| 04 | 班组长，现场或打印 | 责任链、措施、时间线、签字位 | 1240×1754 A4 打印，已派单态 |
| 05 | 技术复核 + 调度，台风前 48 h | 排序怎么来的 + 可执行清单 | 1920×1200 平板，规划态 |
| 06 | 班组长，作业前交底 | 把围挡与交通导改边界画清楚 | 1600×1200 说明图 |
| 07 | 技术复核，办公室平板 | 判读倾斜序列、确认优先序 | 1200×1600 复核态 |
| 08 | 认养居民，手机或张贴在树池边 | 看懂自己那棵树的好处与双方的承诺 | 1080×1620 长期态 |
| 09 | 值班室，雨后 6 h 对内通报 | 已核实／待核实分开上报 | 1440×2000 快报 |
| 10 | 上级主管，会议室投屏 | 覆盖率、谁没报、哪些数暂时不能用 | 1920×1080 年度态 |

## 3. 这十件共同证明的三件事

1. **同一棵数在六个介质里是同一棵**。件-01 报的 TZ-JS-0417（香樟，胸径 62 cm，
   高 14.2 m，冠幅 9.4 m，倾斜 6.8°，空洞 34 cm，风险分 76 → 立即处置，路段建设路，
   末次巡检 2026-09-28，巡检员陈拓）在件-02 档案、件-04 处置单、件-08 认养卡里
   **逐项一致**（这四件携带完整档案）；件-05/06/07/10 引用同一棵树与其中部分字段
   （树号、冠幅 9.4、路段建设路），不重复整份档案。派单与复测时刻在件-04/08 对得上。
   本条为收尾时脚本回查十份 `final.snapshot` 后改写，原文把六件并列、暗示整份档案
   在六件中都出现，超出实际。
2. **总量在统计图里互相对得上**（下式为脚本回查十份 `final.snapshot` 的实际出现位置）：
   立即处置 98 → 件-01/03/05/06/09/10；在册 3,725 → 件-03/09/10；工单 327、超时 87
   （26.6 %）→ 件-03/09/10；90 天覆盖率 24.9 % → 件-03/10；超一年未巡检 726 → 件-03/09/10；
   灾后 113 起 → 件-07/09/10；遮荫 69.4 m² → 件-08/10；−11 户 → 件-08/10。
   **限期 229 只印在件-03**；**观察期 669 与正常 2,729 没有印在任何一页上**——件-03 的
   条形明确标注"条长＝非正常棵数，不含「正常」"，这两个数只存在于数据集与本文，
   四者求和 3,725 是数据集层面的校验，不是页面上的可见事实。
3. **数据缺陷写在页面上，不藏在脚注里**。这是本题刻意坚持的做法：

   | 缺陷 | 出现在 | 页面上的处理 |
   | --- | --- | --- |
   | 岩前街道净增认养户数 = **−11** | 件-08 红字、件-10 ④ 行 + ③ 红色级 | 直接写"退回核对中"，不四舍五入、不改成 0 |
   | 云屿街道压线 0 起但阻路 15 起 | 件-09 ③、件-10 ④ | 判为"疑未单独登记"，列入 1.5 人·日补录 |
   | 灾情上报 113 起未去重，30 起待核实 | 件-09 ①②、件-10 ③ | 已核实／待核实分列，不合并成一个总数 |
   | 南门街道在册最多（948 株）只报 4 起、静默 6 h | 件-09 ②、件-10  | 用"每千株上报 4.2 vs 全市 30.3（约 1/7.2）"改判为疑漏报 |
   | 两套冠幅公式：π(D/2)² vs 0.72·D² | 件-08（69.4 m²）与件-10 ⑤（63.6 m²） | 两式两数与 9.1 % 差值同页写出，不事后统一 |
   | 认养未落到单株 → "认养树达标率"算不出 | 件-10 ③ 红色 + ⑤ 第 2 笔账 | 明确写"字段缺失，不是巧合"，并给出 3.0 人·日补齐方案 |
   | 件-07 的 2026-09 风速为 0 节 | 件-07 页内说明 | 标注为缺测，不当作"无风" |
   | `wind_kts` 是逐月点采样而非过程极大值 | 件-09、件-10 页脚 | **拒绝引用风力等级**，不写"平均 14 节吹倒 113 株"这类假因果 |

## 4. 假设与验证边界

| 假设 | 现在的证据 | 缺什么 |
| --- | --- | --- |
| 风险分权重能预测倒伏 | 无。只有种子数据的内部一致性 | 至少 3 年"判级 → 实际倒伏"回溯，算命中率/漏报率 |
| 市民愿意为"能被认出来"多填两个字段 | 无 | 件-01 的完成率对照实验 |
| 3 米外可读的大屏字号够用 | 只有我自己按 2560×1440 排版目测 | 真机 + 真实值班室照度下的可读性测试 |
| 打印处置单在雨天现场能用 | 无 | 纸张、覆膜、手套操作下的字迹实测 |
| 覆盖率 60 % 目标是合理目标 | 产品自定 | 行业基准或上级考核口径 |
| 认养承诺"每 90 天内一次"可兑现 | 反例：当前只有 24.9 % 达标 | 件-10 ⑤ 的 18.1 人·日补数账能否排进预算 |

`journey.json` 逐件标注它验证的是哪个假设、缺哪一步证据。

## 5. 诚实声明

- **未做真实用户验证**：没有访谈、没有可用性测试、没有任何一件经过真实用户操作。
  上面所有"谁在什么环境下用"是对角色的合理设定，不是观察结果。
- 权重、阈值、60 % 目标、人均 40 株/人·日、三色可信度分级，全部是**产品自定口径**，
  各件页脚已逐条标注，不冒充行业标准。
- 曲线（树冠、根系、导改弧线）是用 DSL 图元逼近的示意，不是植物学图示；服务无矢量
  path，件内已注明。
- 界面里的可点控件只画"该件能解释其作用"的那些；件-06 是说明图、件-09/10 是通报与
  投屏静态图，因此它们没有导航栏，不是漏画。
- 件-08 画布由计划 1080×1440 改为 1080×1620：v01 在 1440 下三块内容溢出卡片、底部
  互相压字，改画布比压字号或删证据更诚实（记录在 `tmp/<run>/B05/PLAN.md`）。
