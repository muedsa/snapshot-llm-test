## 3. 两个下界与最优性

| 项 | 值 |
|---|---|
| 依赖关键路径 | 255 分钟（R01 → R04 → R07 → R09 → R10 → R12） |
| 资源工作量下界 | 242.5 分钟（485 ÷ 2） |
| 生效下界 | **255**，依赖下界 255 > 资源工作量下界 242.5，所以约束来自依赖链而非团队产能。 |
| 本解完工 | 260 分钟 |
| 与依赖下界之差 | 5 分钟 |
| 是否可证明全局最优 | **是** |

### 上界

本 `schedule.json` 本身就是一个完工于 260 分钟的可行排程。

### 下界证明

1) 1) 双选任务只有 R05/R09/R12，各自只有 design/engineering 两个合法归属，所以所有可行排程按这三个归属分成恰好 8 类，没有遗漏。
2) 2) 对每一类，在「下一个就绪任务 × 它可选的团队」上做完备深度优先搜索，剪枝用可采纳下界 LB = max_t(est(t) + tail(t))，去重键含每个已排任务的 (start, end, team)。该下界恒不超过真实最优剩余完工，所以剪枝与去重都不会丢掉更优解。
3) 3) 8 类的最优完工分别为 260/260/285/285/285/285/300/300 分钟，最小值 260。
4) 4) 因此全局最优 = min(8 类最优) = 260.0 分钟。

8 类归属各自的最优完工：

| R05 / R09 / R12 的归属 | 该类最优完工（分钟） |
|---|---|
| engineering / design / design | 260 |
| engineering / design / engineering | 260 |
| design / design / design | 285 |
| design / design / engineering | 285 |
| design / engineering / design | 285 |
| design / engineering / engineering | 285 |
| engineering / engineering / design | 300 |
| engineering / engineering / engineering | 300 |

### 为什么不是 255 分钟

依赖关键链 R01→R04→R07→R09→R10→R12 长 255 分钟，要让 R07 在第 85 分钟开工（从而达到 255），R05 必须在 85 分钟前做完。R05 依赖 R01（design，第 25 分钟结束），而 design 在 25–85 已被 R04 占满，所以 R05 只能交给 engineering。engineering 于是必须依次做 R02(20) → R05(30) → R03(40) → R06(45) → R08(65)；R05 不能早于第 25 分钟开始，所以 R08 最早在第 205 分钟结束，R10 最早第 205 分钟开工、第 240 分钟结束，R12 最早第 260 分钟结束。资源与依赖把完工推到 260.0 分钟，比依赖下界多 5 分钟。

## 9. 设计说明

- **三图同源**：所有数字都直接读自 `schedule.json`，绘图代码里不做任何再计算。
  `content-map.json` 的坐标由生成 DSL 的同一段代码顺带记录（`layout-marks-*.json`），
  所以「三图一致」是可以用坐标算术复核的，而不是靠人工目测。
- **依赖用编号索引表达**：题目明确不要求画连线，实际也没画——
  避免交叉线盖住时间块。依赖出现在执行图的索引表、简报的依赖列、
  以及 `schedule.json` / `content-map.json` 的结构化字段里。
- **标签放不下时不缩字**：正文保持 20px（横屏）/ 24px（竖页），
  改用「块内 → 块上条带 → 块右侧空档」三级放置策略。
