## 3. 逐件辨识点

### case-01 · 末班车还有多久

- 受众：夜里准备出发的地铁乘客
- 问题：我现在出发，能不能赶上最后一班车，并在换乘截止前到得了？
- 辨识点：把整条线路做成一根**共享时间轴**：乘客当前的时刻用一条竖线钉在轴上，每一站的可乘窗口从这条线画到发车点，越往右越晚——一眼看出还剩多少时间。

### case-02 · 共享设备预约冲突

- 受众：高校公共仪器平台的预约人
- 问题：我提交的时段和别人冲突了吗？谁占了下一档？
- 辨识点：**设备 × 时段的热力矩阵**：冲突格用高饱和红并写上冲突编号，把「冲突」从一条报错变成图上一眼能定位的红块。

### case-03 · 一炉咖啡的 13 分钟

- 受众：准备自己烘豆的咖啡爱好者
- 问题：这一炉的火力够不够？发展时间落在合格区吗？
- 辨识点：**两条豆温曲线叠在工艺事件竖线上**：回温点、转黄、一爆、下豆四个时刻把曲线切成四段，读图的人不用查表就知道每一段在发生什么。

### case-04 · 今天浇哪几块

- 受众：周末才上楼的社区园艺者
- 问题：今天浇哪几块、跳过哪几块？理由是什么？
- 辨识点：**阈值带 + 一句话处置**：含水量条上叠一条 35–60% 的阈值带，每行右侧直接给「浇 / 跳过」，把读数动作取消掉。

### case-05 · 急诊候诊 · 谁等最久

- 受众：值班护士与导医
- 问题：谁已经等太久了？下一步该叫谁？
- 辨识点：**颜色即分级**：从濒危到非紧急五级各一个颜色，每级一条「最长等待 vs 目标线」的对比条，超时的级别在底部被点名。

### case-06 · 评审队列别压在人身上

- 受众：开源项目的维护者
- 问题：这个 reviewer 该不该再加活？哪些 PR 已经要超 SLA 了？
- 辨识点：**容量用格子表示而不是百分比条**：每人 6 个槽位，装满就是满载，一眼看出该给谁分流——百分比条看不出「差几个」。

### case-07 · 今夜，抬头能看到的

- 受众：刚入门的城市观星者
- 问题：今晚这些亮星在哪个方位？城市光害会不会把矮星吃掉？
- 辨识点：**把 20° 光害淹没带画成一层暗底**：带子里的星只画空心圈并标灰，「看不见」因此是一个**被画出来的区域**，而不是一句脚注。

### case-08 · 明早补什么，今天先动哪几箱

- 受众：门店的品类经理
- 问题：明天早上补什么货？哪几箱今天就得处理掉？
- 辨识点：**一根 SKU 横跨两条风险轴**：左边是缺货（库存 ÷ 安全库存），右边是过期（剩余保质期），最右一列给出动作。两个互不相干的维度合成一行，扫一眼就能取舍。

### case-09 · 哪几个港的关闭窗口短到要提前安排

- 受众：航运公司的值班调度
- 问题：未来 84 小时里，哪几个港的关闭窗口短到必须提前安排？
- 辨识点：**每个港口单独一行，而不是共用一根时间轴**：六条时窗叠在同一轴上时会糊成一条实心带，谁也读不出来；拆成六行后，警戒与关闭两段一分得清。

### case-10 · 哪块地不能再进人

- 受众：音乐节的舞台安全官
- 问题：现在哪个分区超过红线了？下一批人该往哪儿引导？
- 辨识点：**把场地画成真的平面图**：分区位置、尺寸、出入口都按比例摆，安全官看的是「哪一块」，抽象热力图反而不好定位。

## 4. 真实文档与 DSL 能力应用

| 来源 | 用到的结论 |
|---|---|
| https://open-snapshot.muedsa.com/ai-guide.md | 请求体与响应形态；`type="png"` 决定编码；响应为原始 PNG 字节 |
| https://snapshot.muedsa.com/reference/parser-tags/ | 39 个标签总表：`Container`/`Positioned`/`Stack`/`Text`/`Transform`/`ClipRRect` 等 |
| 同上 · `Transform` | `matrix` 为列主序 4×4、**16 个**有限 Float、外层带括号且值间无空格。首版写了 17 个值直接 400；改正后用它画折线、斜条与旋转块 |
| 同上 · `Text` | `textAlign` 合法取值是**大写** `START`/`CENTER`/`END`/`JUSTIFY`（A23 探针已验证）；小写一律 400 |
| 同上 · `Container` | `border` 格式为「宽度 样式 颜色」；`borderRadius` 做卡片、槽位与色块圆角 |
| `GET /fonts`（run 级共享准备） | Inter / Inter Semi Bold / Inter Medium 与 Noto Sans CJK SC |

**十件全部没有使用 `<Image>`**：没有外部素材，也没有内嵌任何已渲染图。
每件都是「用参数生成 DSL → 渲染 → 看图 → 改参数 → 重渲染」。

## 5. 一个被推翻的旧结论

本题开工时沿用了本套早先记录的一条「服务行为」：`textAlign` 不可用。
A23 已经用探针证明它只是要求**大写**枚举，B01 全部改用
`textAlign="END"` / `"CENTER"` 做右对齐与居中，不再靠估算字宽手工摆坐标。
更正过程与证据见 `tmp/run-20261011-01/_suite/capability-corrections.md`。

## 7. 未解决事项

- 无影响交付的未解决问题。
- **十件的场景与数据都是自拟的**，这一点在 `portfolio.json.disclaimer`、
  每张图的页脚和每份 `case.md` 里都写明了，没有把它们包装成真实客户作品。
- **服务偶发返回 HTTP 200 + 0 字节**：十件的渲染循环都校验了 PNG 字节长度并重试，
  失败响应原样保存在 `tmp/run-20261011-01/B01/responses/`。
- **文字宽度是估算值**：`bsnap.em_width` 用 A14 实测标定的系数判断「放不放得下」，
  多行段落一律自己排版逐行输出（`wrap` + CJK 悬挂标点），
  不依赖服务端自动换行——服务端会把溢出盒子的行**静默裁掉**。
  估算仍可能偏小，所以每个 Text 盒子都留了余量。
