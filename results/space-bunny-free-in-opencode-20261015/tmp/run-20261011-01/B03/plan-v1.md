## 全局完成标准（GD）

| ID | 条件 | 检查方法 |
|---|---|---|
| GD-1 | 每件都是 open-snapshot 的真实 200 响应，PNG 字节数 > 0 | `requests.jsonl` status=200 且 response_bytes>0；PIL 复核尺寸 |
| GD-2 | 每件有同名完整 `final.snapshot`，DSL 内无 `<Image>` | `grep` 全部 final.snapshot |
| GD-3 | 正文字号 ≥ 18px；表格编号类 ≥ 16px 且在 case.md 说明原因 | 读生成脚本的 size 参数 + 实际看图 |
| GD-4 | 无静默裁字：所有单行文本宽度 ≤ 盒宽（生成时 assert） | `b03kit.assert_fits` 在生成期抛错 |
| GD-5 | 无内容越出画布（生成时 assert） | `b03kit.guard` |
| GD-6 | 每张图页脚写明「自拟场景与自拟数据 · 非真实记录」 | 逐图看页脚 |
| GD-7 | 每张图都实际打开看过；发现的缺陷有对应 iterations.jsonl 记录 | 看图记录 + 逐条观察 |
| GD-8 | 十件的场景/手法互不重复：没有两件靠同一套手段成立 | 逐对自查（见下表「独占手法」列） |

## 计划变更

### 变更 A · case-06 从「仓库货位热区平面」改成「等轴测动线图」（首渲后追加）

- **原标准 G1**：`case-06 用平面热力图呈现 12 个货位的拣货频次分层 + 3 条动线`。
- **首渲暴露的问题**：平面图里「动线」只能是几条折线，
  看不出它绕过了什么、经过了哪些巷道，也无法体现「哪一排货架更密」。
  实际做出来（v1，平面 + 热力 + 折线）信息量不足，
  不符合「仓库主管要在 30 秒内判断动线够不够」的完成标准 GD-3。
- **依据**：v1 的实际渲染（`outputs/run-20261011-01/B03/case-06/final.png` 的 v1 版本，
  留痕在 `tmp/run-20261011-01/B03/iterations.jsonl` 的 case-06 记录）。
- **新标准 G1'**（生效版本 v2 起）：
  `用等轴测投影画 12 个货位，柱高与颜色双编码今日拣货单量，
  四条动线（外环三 + 主巷道一）画成始终可见的规划叠加层`。
- **理由**：`Transform` 仿射矩阵是本 run 探针确认可用、但十件里还没有主导作品使用的能力；
  等轴测让「高度 = 业务量」这条冗余编码在 3 米外成立。

### 变更 B · case-08 从「逐时表 + 仪表」改成「去色插画 + 唯一彩色数据层」（首渲后追加）

- **原标准 G2**：`case-08 用 SWEEP 仪表环 + 24h 趋势 + 逐时建议表回答开窗问题`。
- **首渲暴露的问题**：v1 把背景画成彩色插画，导致浅色文字压在彩色背景上读不清；
  而这张图是要转发到业主群的，**彩色背景本身就会抢走注意力**。
- **依据**：v1 实际渲染（浅色副标题几乎看不见）。
- **新标准 G2'**（生效版本 v2 起）：
  `背景插画整层用 ColorFiltered blendMode=SATURATION 去色并压深色蒙版，
  画面中唯一有颜色的必须是数据层；仪表环改为 6 段弧形 ClipPath 按 AQI 分档上色`。
- **理由**：`ColorFiltered` 是探针确认可用、当时还没有主导作品使用的能力；
  而「颜色从装饰变成编码」正好回答这张图为什么要转发。

### 变更 C · case-07 两栏对齐方式（首渲后追加）

- **原标准**：`两栏正文都用服务端 textAlign="JUSTIFY"`。
- **首渲暴露的问题**：左栏因为要做首字下沉只能自己排行，
  于是两栏右缘不齐——在一张印刷内页上这是明显的破绽。
- **依据**：v1 实际渲染（左右两栏右缘明显不齐）。
- **新标准**（生效版本 v2 起）：
  `右栏整段交给服务端 JUSTIFY；左栏自己排行后按目标宽度逐行计算 letterSpacing 撑齐
  （字距超过 3.2px 的行不撑）`。
- **理由**：服务端的断行结果无法预测，逐行微调字距是唯一可保证齐尾的办法；
  这条也写进了 `b03kit` 的 `justify_spacing()`。
