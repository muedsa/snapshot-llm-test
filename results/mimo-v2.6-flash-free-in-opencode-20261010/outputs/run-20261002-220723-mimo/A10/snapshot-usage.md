## 3. 六格内容与逐格证据

### ① 每个矩形各自 50% alpha

- 实现：`#FF000080` @ 区局部 `(40,40,160,120)`、`#0000FF80` @ `(120,80,160,120)`，蓝在红之后绘制（`S02`、`S03b`）。
- 解析解（double 精度按 8 位 alpha 逐步复合再取整）：
  - 红区 = `(255,127,127)`，实测 `(255,127,127)` → **Δ0**
  - 蓝区 = `(127,127,255)`，实测 `(127,127,255)` → **Δ0**
  - **重叠区 `(180,100)` = `(127,63,191)`，实测 `(127,63,191)` → Δ(0,0,0)**（`X01`/`X04`）
- 重叠区画了一个黑色断口十字（四条臂分别在 x164…171 / 188…195 与 y84…91 / 108…115），**中心 (180,100) 那一个像素四条臂都不覆盖**，`X06` 实测十字臂 R 值 < 60 而中心点仍精确等于解析解，证明标记没有污染采样。

### ② 同样两个不透明矩形放进 `Opacity(0.5)` 组

- 实现：组内红蓝都是**不透明**、坐标与 ① 完全相同，整组只做一次半透明（`S03`）。
- 解析解：组内蓝完全盖住红 → 组内重叠 = 纯蓝 `(0,0,255)`，再乘 0.5 叠白 = `(128,128,255)`；**实测 `(126,126,255)`，Δ(−2,−2,0)**，5×5 邻域均值同样稳定（`X02`/`X05`）。
- 容差 **±2 LSB**：解析解是精确有理数，渲染器在 8 位预乘空间里算，而 `0.5×255 = 127.5` 本来就不可整除，最坏可差 2 个最低位。容差理由写在 `composite-audit.json` 的 `sampling.tolerance_rationale`，没有把它当成"恰好等于"。

### 128/255 与 0.5 到底差在哪（题面要求解释）

`composite-audit.json` 的 `sampling.difference.explanation_128_255_vs_0_5` 逐条给出，要点：

1. `0x80 = 128`，所以 ① 的 alpha 是 `128/255 = 0.5019607843`，比 ② 的精确 `0.5` **高 0.0019607843（约 0.196%）**，换算成 8 位就是 `0.5 + 1/510`。
2. 更要紧的不是这 0.196%，而是**复合次数**：① 里蓝层是叠在"已经合成过的红叠白"之上，乘的是 `1 − 128/255 = 127/255 = 0.498039`；② 里蓝先在组内不透明地盖掉红，再对这一层压平后的结果**只做一次** 0.5。
3. 结果在同一个点上：① `(127,63,191)` vs ② `(126,126,255)`，**最差通道差 64**（`X03`）。绿通道最响：`0.498039×127 = 63.3` 对 `0.5×255 = 127.5`，差 64.2/255，读出来就是两种不同的颜色。
4. 所以"每个形状各自 50%"和"整组 50%"不是同一件事，板上把这个差别直接摆在标出来的那个点上。

### ③ 只模糊背景

- 实现：全区锐利条纹（16px 周期、8px `#94A3B8` 实条 + 8px 白）先画；然后 `ClipRRect(240×160, r20)` 内放**只有条纹层**的 `ImageFiltered(σ=6)`（条纹按区坐标偏移 −40,−40，与外面严格对齐）；文字与红条画在滤镜**外面**。
- 顺序是"先模糊、再裁剪"，因为 `ImageFiltered` 会按 sigma 自动外扩输出边界；若先裁剪再模糊，卡边会出现向内塌陷的半透明晕。条纹数据覆盖整张卡 ±18px，卡内不存在"模糊采到空白"的边缘伪影。
- 实测（`X07`/`X08`）：卡外 30px 行程红通道跨度 **107**（满对比 148…255，锐利）；卡内同 y 行程 **≤ 40**（条纹被抹平）；文字框 R 对比度 **194**（锐利）。

### ④ 子树整体模糊

- 实现：`ClipRRect` → `ImageFiltered(σ=6)` → `Stack{ 条纹偏移层, 文字, 红条 }`，即**卡内文字与形状一起进子树**。
- 实测（`X09`/`X10`）：卡外跨度 **107**（仍锐利）、卡内 **≤ 40**、文字框 R 对比度 **58**，与 ③ 的 194 **相差 136** —— 差异正好落在题面要求的位置上。

### ⑤ 先 `ColorFiltered(MULTIPLY)` 后子树高斯模糊

- 实现：`ColorFiltered(#F6B94A, MULTIPLY)` → `ImageFiltered(σ=6)` → 子树（通栏深色条 + 两块中间留**透明间隙**的深色矩形 + 带 `boxShadow` 的底条）。
- 实测：
  - 透明间隙点 = `(218,165,67)`，是金色而非白色 —— 文档说的"部分混合模式会给边界内的透明间隙着色"被真实像素复核过（`X11`），没有当成已知结论照抄。
  - 底条下方 = `(164,126,52)`，金色被阴影压暗 → **阴影确实保留**（`X15`），对应文档"保留合法溢出和阴影"。
  - 子树外一点 = `(255,255,255)`，滤镜不外溢（`X12`）。
  - 被着色区域的局部包围盒 = `x 42…277, y 12…238`（236×227）—— 比 180×180 的子树大，因为它按文档说的"模糊输出边界"外扩了 sigma，又包含阴影溢出。这个事实照实写进 `X14` 的 detail，没有粉饰成"正好 180×180"。

### ⑥ 同样的 ⑤ 效果 + 圆形裁剪

- 实现：`ClipOval(ANTI_ALIAS)` 包在 ⑤ 的最外层，子树与 ⑤ **完全相同**。
- 实测：圆内间隙 `(218,165,67)`、圆外同相对位置 `(255,255,255)`（`X13`）；被着色区域从 ⑤ 的 236×227 矩形收缩成 `x 75…243, y 76…209` 且被限制在圆盘内（`X14`）。**矩形 → 正圆这个形状变化本身就是裁剪边界**，`zoom-clip.png` 里一眼可读。

## 4. ±容差与核对方法（写在 `composite-audit.json` 的 `verification_method`）

1. **PNG**：签名 `89 50 4E 47`；IHDR 字节 16..23 按大端 `int32` 读（先 `[int]` 再乘权值）。
2. **DSL**：重读交付件 `.snapshot`，查无 BOM、按 XML 解析，再按题面点名的结构数标签与属性（区、卡、Opacity、ClipRRect、ClipOval、ImageFiltered、ColorFiltered、矩形坐标、绘制顺序）。
3. **合成**：用题面给的 alpha 在 double 精度下独立算出解析解，再用 `Bitmap.GetPixel` 读交付 PNG 上区局部 `(180,100)` → 画布 `(340,370)`。5×5 邻域求均值，用来证明取的是稳定内部像素而不是边或十字像素。容差 **±2 LSB**，理由写死在文件里。
4. **锐/糊**：30px 行程的红通道 max−min，卡外与卡内同 y 对比。满对比条纹理论跨度 107、实测 107；阈值写成"范围"而不是"单边位置"，因此**反走样只会略微缩小范围，不影响判定**，也就不需要给单边留例外。
5. **裁剪边界**：按金色判据 `R>180, B<160, R−B>60` 求每格被着色像素的包围盒，⑤ 给出未裁剪的作用区、⑥ 给出被圆盘裁过的作用区，再补一个圆外点必须是纯白。
6. **不裁切**：全画布扫描所有与页面底色不同的像素得到墨迹包围盒，并单独检查最后一行。

**结果：41/41 PASS，0 失败。** 采样解析解 vs 实测最坏 2 LSB，恰好等于所声明的容差（`all_within_tolerance: true`）。

## 7. 本题踩到的坑（跨题可复用）

**DSL / 服务**

1. **`Stack` 默认 `clipBehavior="HARD_EDGE"` 会把溢出子节点裁掉**。② 里若把 `Opacity` 组的 `Stack` 按矩形尺寸来放，蓝矩形会溢出被裁；③④ 里条纹层要靠 `left="-40" top="-40"` 溢出到卡外，也一样。两处都必须显式 `clipBehavior="NONE"`，裁剪只交给 `ClipRRect` / `ClipOval`。
2. **"先模糊再裁剪"**。`ImageFiltered` 按 sigma 自动外扩输出边界，把裁剪放在它外面，卡边才是干净的圆角；反过来会得到一圈向内塌陷的半透明晕。
3. **`ColorFiltered` 的作用范围 = 子树绘制边界（含模糊外扩与阴影溢出）**，所以 ⑤ 的金色区域是 236×227 而不是 180×180。这是文档行为，实测确认，不要按自己想象写"正好子树大小"。
4. `Text` 带 `width` 时**会软换行**，超长的单行会被折到第二行，再被画布底边裁掉——本次唯一的视觉缺陷就是这么来的。页脚这类长句要**主动拆成多行短句**，别指望它一行放得下。
5. `fontFamily="Inter,Noto Sans CJK SC"`、`#RRGGBBAA` alpha 在最后两位、`boxShadow="x y blur spread color"`、`textAlign` 需要 `width` + `height` —— 沿用前几题结论，全部实测可用。
6. BOM 仍会让解析落到 `400 PARSE_ERROR: Not Support RAWTEXT`，一律 `[System.IO.File]::WriteAllText(p, s, [Text.UTF8Encoding]::new($false))`。

**PowerShell**

7. **`-f` 左右操作数之间不能换行，哪怕整个表达式在括号里**。`('fmt'\n -f $a, $b)` 会报 `Missing closing ')' in expression.`，因为换行后括号表达式被视为已完整结束。本次 `gen.ps1` 就是这么挂的；改法是把格式串先赋给变量再在同一行 `-f`。
8. **逗号比 `+`/`-` 结合更紧**。`return ,@($minx - $cx, $miny - $cy, ...)` 实际是 `$minx - ($cx,$miny) - ...`，直接抛 `does not contain a method named 'op_Subtraction'`。数组字面量里每个表达式都要单独加括号。
9. **变量大小写不敏感**。`foreach ($z ...) { $zx = $ZX[$z % 3] }` 里的 `$zx` 就是 `$ZX`，第一次循环就把数组覆盖成一个整数，下一次报 `Cannot index into a null array`。循环临时变量必须换名字（本次改 `zi/gx/gy`）。
10. 数组字面量里拼接同理要加括号：`@([char]0x2460 + '文字', ...)` 会被解析成 `[char]0x2460 + ('文字', ...)`。做法是先把 `[char]` 转成 `[string]` 变量再 `('' + $C1 + '文字')`。
11. 方法参数不会被展开，`List[object].Add((Rgb x y))` 能存住一个 `int[3]`；但 `$a += (Rgb x y)` 会把它**摊平成三个元素**，需要 `,$(...)` 或者干脆用 List。
12. `function Foo` 与别名/cmdlet 的优先级问题（`MP`、`MM`、`Diff` 三案）已连续三题复发，新函数名落笔前先想一遍有没有撞名。
13. 读 PNG 尺寸必须 `[int]$b * 16777216 + …`；`[byte] -shl 8` 按字节截断，`6 -shl 8 = 0`，会量出假尺寸。
