### 问题细节

**问题 1（v02 → v03，内容）简报的依赖总览不完整。**
看 `attempts/v1/decision-brief.png` 时，分层区只画了 `L0…L5` 与各层任务 chip，没有告诉读者 R07 具体依赖哪几个任务；而题面明确要求简报展示依赖概览。这是**渲染成功但视觉上不满足需求**的典型问题，不能因为 HTTP 200 就当合格。修复后简报上能逐条读出 16 条边：`R03←R02、R04←R01、R05←R01、R06←R03、R07←R04,R05 / R08←R04,R06、R09←R07、R10←R07,R08,R09、R11←R08,R09、R12←R10,R11`。

**问题 2（v02 → v03，可读性）分层内顺序混乱。**
`Where-Object` 没加 `Sort-Object`，沿用排程表按结束时间的顺序，于是 L1 显示 `R04 · R05 · R03`。加 `Sort-Object { $_.id }` 后为 `R03 · R04 · R05`，与编号直觉一致。

**问题 3（v02 → v03，语义）「起始」易误读。**
`deps.Count -eq 0` 时输出 `起始`，但该行在图例里对应的是「前驱编号」，读者容易当成开始时刻。改为 `无前驱`。

**问题 4（v02 → v03，排版）团队胶囊顶边。**
`engineering` 11 个字母在 fontSize 20 下约 115px（估算器给 123px），胶囊只有 130px，两侧各余约 8px 且第 3、4 列只剩 12px 间距。列宽重排后胶囊 144px，两侧留白约 10px，列间距 12/12/4→实测列间 12、8。

**问题 5（工具，自身 bug）`TW()` 宽度估算器大小写失效。**
PowerShell 的 `-match` 默认大小写不敏感，`$ch -match '[A-Z]'` 会命中小写字母，`engineering` 被算成 154px 而不是 123px，触发了问题 4 的断言假阳性。改为码点区间判定后估算器才可信。这条属于「本次实际遇到并确认」的坑，不是从文档读来的注意事项。

**问题 6（流程，已修正）`schedule.json.brand = null`。**
`sched-a24.ps1` 写 `brand = $rel.'brand'`，而 `inputs/release.json` 顶层只有 `start/deadline/teams/tasks/risks`，没有 `brand`，于是交付 JSON 里出现 `brand: null`。已改为题面品牌并补 `brand_source` 说明；重新生成后逐行比对只有 `generated_at`/`brand`/`brand_source` 三行变化，12 任务数据完全一致；用新 `schedule.json` 重生成的三份 DSL 与交付 `.snapshot` 逐字节相同，因此**未重渲染、未动 PNG**。首版 JSON 归档在 `attempts/v1-schedule/`。

1. **两次文档错误响应体被后续同名请求覆盖。** `A24-doc-002`（403，1395 B）写到 `doc-widget-text.md`，随后 `A24-doc-005`（200，56943 B）用同一路径把它覆盖；`A24-doc-004`（404，20017 B）写到 `doc-widget-container.md`，随后 `A24-doc-006`（200，64460 B）覆盖。**这两个 403/404 的响应正文已无法恢复**，是本任务的留痕缺失。两次访问的 URL、状态码、字节数、耗时与时间戳在 `requests.jsonl` 中逐行保留，未丢失；后续取文档一律先落到带编号的唯一文件名（见 §2 中 `doc-*.md` 均为不同 URL 的成功响应，无再覆盖）。

## 7. 设计选择、经验与未解决事项

### 关键设计选择

1. **单一数据源**。排程先由 `sched-a24.ps1` 求解并落 `schedule.json`，三张图的生成器只读它、不各自算时间。这是「三图不得矛盾」的结构性保证，而不是靠人工对数字。
2. **等比时间轴**。`x = 24 + minute × 1884/420` 用同一个函数产生所有任务块的 `left` 与 `width`，空档、缓冲带、完成线、截止线也走同一映射，天然满足「真实时间按同尺度绘制」。
3. **依赖用编号索引而不是连线**。DSL 没有 line 元素，画 16 条依赖线必然交叉并盖住任务块。改为：执行图在块内给前驱编号、简报给「分层 + 16 条边两行」、卡片按时间序，三处都不画线。
4. **团队不塞进任务块**。`engineering` 全称约 106px，而最窄块（`R02` 20 分钟 = 89.71px，内宽 81.71px）放不下；强行塞会溢出。改为泳道胶囊 + 同色填充 + 图例文字「任务块所在泳道即所属团队」表达，全称在简报与卡片胶囊中给出。**没有**为了塞下文字而缩字号（那会跌破横屏正文 ≥20 的下限）。
5. **虚线与斜纹用矩形拼**。没有 line 元素，`16:00 截止线` 用 5px 实心 + 15px 间隔的矩形序列拼成虚线，空档用倾斜矩形拼斜纹。
6. **宽度护栏前置**。生成器带 `TW(str, fs)` 宽度估算器，对每个标签、图例、卡片副标、依据行、风险行、页脚、依赖边行做「超宽即 throw」的硬校验；布局带 `footerY ≤ limit` 断言。这让问题在**渲染前**暴露，而不是渲染后靠肉眼找。

### 可复用经验（本套已再次验证）

1. **PowerShell 5.1 没有 `??` 和三元运算符**，要用 `if`/`-or` 显式写。
2. **PowerShell 变量大小写不敏感**：`$cw2` 会覆盖 `$CW2`、`$gaps` 会覆盖 `$GAPS`、函数参数 `[bool]$B` 会与局部 `$b` 冲突导致 `''` 被强制成 `$false`。本题已因此踩过并改名（`$halfW2`、`$GAPST`、`$schedGaps`、`$boldAttr`）。
3. **`-match` 默认大小写不敏感**：`$ch -match '[A-Z]'` 会命中小写字母，做字符分类必须用 `-cmatch` 或码点区间。本题问题 5 即此。
4. **命令调用后跟算术会静默丢掉后半段**：`PX ([int]$t.end_min) - $bx` 实际只求值了 `PX(...)` 且不报错，必须写成 `(PX (...)) - $bx`。本题全部点位都按括号版写。
5. **`r` 是 `Invoke-History` 的别名**：函数名 `R` 会被吃掉，改名 `Box`/`Txt`。
6. **`[IO.File]::AppendAllLines` 要 `[string[]]`**，`UTF8Encoding($false)` 才不带 BOM。
7. **`[Math]::Ceiling(TW $x 22)` 需要内层括号**：`[Math]::Ceiling((TW $x 22))`。
8. **硬编码 DAG 层号容易违反前驱优先**，要用不动点迭代 `layer(t) = 1 + max(layer(deps))` 计算。
9. **同名响应文件会互相覆盖**：为每个文档请求准备唯一文件名，否则失败响应体（403/404）会被后续成功请求覆盖 —— 本题就因此丢了 2 个错误响应正文，已记入过程偏差。
10. **「HTTP 200 ≠ 视觉合格」**：本题三张图第一次渲染全部 200，仍从看图中发现 5 个真实问题（依赖概览不完整、层内顺序、语义标注、胶囊顶边、估算器 bug）。

### 结束依据

不是「达到某个迭代次数」而结束，而是：**11/11 指定交付齐全** → 生成器 `problems = 0`（含依赖边 16/16、页脚安全区、块内零溢出）→ 三张最终 PNG 全部为服务真实响应字节、与同名 `.snapshot` 配对 → **逐张用图像查看工具打开确认**并按上表逐条核对尺寸、正文最小字号、内容与三图一致性 → `schedule-audit.json` 7 项校验 `all_pass = true`、`problems = 0`。

### 未解决事项

- **过程偏差**：2 个文档错误响应正文（403/404）与第 1 次 400 的 `.body` 被同名请求覆盖，无法恢复；其 URL/状态/字节数/错误摘要仍完整留在 `requests.jsonl`。
- **看图精确时钟**未采集，只给可证明时间窗。
- **token / 图像输入 / 费用**：平台未提供，`task-metrics.json` 记 `null` 并注明来源与覆盖范围，未用字符数或账号余量估造。
- **最优性**：题面不强制证明；本任务在 `schedule-audit.json.optimality` 给出了**可核验的完整情形枚举证明**（`proven = true`，枚举全部 8 个可分配任务的分配情形 + 每种情形下的 4 种合法排序，下界 260 = 候选 260），因此三张图上才敢写「最优」。这是额外交付，不是必需项。
