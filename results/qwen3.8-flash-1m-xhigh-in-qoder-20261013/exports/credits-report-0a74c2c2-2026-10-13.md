## 四、放大机制：为什么 51.9 万 token 花了 8.08 亿的钱

每次请求都要把"系统提示词 + 全部历史 + 新内容"整体发一遍，所以成本 = Σ(每次请求的上下文规模)，而不是 Σ(新产生的内容)。report.json 用 `amplification = 计费总量 ÷ 净上下文 = 1,557.6×` 表达这个比值。

最直接的机械证据是系统提示词：本体只有 **23,052** token，却被计费 **61,341,372** token —— 61,341,372 ÷ 23,052 = **2,661**，正好等于请求轮次。也就是说，一段永远不会变的内容被完整重发了 2,661 次，仅它就值 163 credits。

按单次请求上下文规模分桶，成本高度偏向"上下文已经很胖"的后段请求：

| 单次请求上下文 | 请求数 | 请求占比 | 计费 token | 成本占比 |
|---|---|---|---|---|
| <10 万 | 345 | 12.97% | 22,686,626 | 2.81% |
| 10–20 万 | 509 | 19.13% | 77,204,498 | 9.55% |
| 20–30 万 | 485 | 18.23% | 120,513,216 | 14.91% |
| 30–40 万 | 465 | 17.47% | 163,670,785 | 20.25% |
| 40–50 万 | 462 | 17.36% | 208,286,742 | 25.76% |
| 50–60 万 | 395 | 14.84% | 216,048,476 | 26.73% |

**上下文 ≥40 万的 857 次请求（占请求数 32.2%）贡献了 52.49% 的总成本。** 单次请求的边际成本随上下文线性变化：在最终上下文 519,022 下每多发一次请求是 1.379 credits，在峰值 599,816 下是 1.593 credits —— 这就是"多一轮无谓自检 ≈ 1.4 credits"的定价。

一个可迁移的直觉换算：一份 3 万 token 的文件只要还在上下文里，每 1,000 次请求就消耗 80 credits。所以"内容写多大"远不如"内容活多久"重要。

两点值得注意：

2. **Write 的"单次调用平均计费"高达 539,178**，是 Bash 的 4.2 倍：整文件一次性投进上下文后，要陪着后续几乎所有请求重发。而 Edit 单次只有 126,152 —— 同一处修改用 Edit 而非重写整文件，成本差约 4 倍。
3. **WebFetch 只有 3 次、101,178 token（0.01%）**，网络抓取在这条会话里几乎不构成成本；压力全在本地执行链路上 —— Bash + Write + Read + Edit 四项合计 460,591,790 token = 总计费的 **57.0%**。

## 九、时间与耗时口径（不把工作时长当成计算时长）

report.json 提供的只有分钟粒度的请求时刻，**没有任何单次请求耗时数据**：`proxy.matched = 0`、`logExists = false`、`configured = false`（代理链路未真正生效，详见第十节第 6 条），`linkHealth.usageSource = transcript-ratio`。因此：

- 墙钟跨度：`startedAt → endedAt` = **24 小时 12 分**（本地 10-12 10:09 起，10-13 10:21 止）。
- 由请求时刻重建：相邻请求间隔合计 1,452 分钟 ≈ 整个跨度，其中 8 个间隔超过 5 分钟、最长 10 分钟（本地 14:44、15:30 附近）。请求流基本连续，没有数小时级的人工空档被计入执行窗口。
- **这 24.2 小时不能解释为"24.2 小时的模型计算时间"**：分钟粒度无法区分模型推理、本地长命令执行（例如批量渲染脚本）与真实空闲，>5 分钟的那约 62 分钟尤其无法归属。`88.7 credits/小时`、`71.58 credits/题` 只是把总消耗摊到墙钟与题数上的平均值，不是速率指标。
- `endedAt` 与 `generatedAt` 只差 0.46 秒，说明它是**本次采集时刻**而非会话的自然结束点；统计之后同一会话若继续执行，这部分不在本报告内。
- 按小时分布（本地钟点，24.2 小时窗口几乎覆盖一个完整昼夜循环）：消耗峰值在 06:00（7.60%）与 01:00（6.45%），低谷在 14:00（1.16%）、15:00（1.55%）、16:00（2.33%）。低谷三级恰好紧跟第 1 次压缩（本地 13:48）：这三个小时共 198 次请求、40,745,053 token，平均每请求 205,783 token；而 01:00 那一小时 102 次请求平均每请求 511,416 token —— **同样的请求动作，只因上下文更瘦/更胖，单价差 2.5 倍**，这是第四节结论的小时级印证。完整 24 行明细见 [`tmp/hourly.md`](../tmp/hourly.md)，未列入正文以免与结论等权。

## 十、优化建议（按可省 credits 排序）

以下都是基于 report.json 实测结构的**建模估算**，不是承诺值；实现压缩/摘要策略变更会影响任务连续性，需要配合质量自检评估。

1. **把自动压缩触发点从 60% 压到 40–50%（最大单项杠杆，省 267–620 credits）。** 压缩后基线约 3.2 万，平均上下文 ≈（基线 + 触发点）/2：触发点 50 万 → 平均 26.6 万，总计费 −12.43%（省 267 credits）；45 万 → −20.66%（省 444）；40 万 → −28.89%（省 620，总量降到约 5.75 亿 token）。代价很小：压缩次数由 6 增至约 7.3–9.3，压缩自身输入成本仍是约 10 credits。**质量风险：** 摘要更频繁意味着更早丢失细节，30 题连续执行与 A21/A22 三轮回归依赖历史细节，需要靠每题的 `task-metrics.json`/DSL 落盘来补偿上下文丢失，不能只靠对话记忆。
2. **Bash 输出瘦身（减半 ≈ 省 270 credits）。** Bash 现在占 25.12%，且平均每条命令结果在上下文里活 186 个请求。做法：长输出命令统一 `| tail -n 40` / 只回摘要与退出码；不要把完整 DSL、base64 图像或整份 JSON 打到 stdout（改写入文件后按需 Read 片段）；把多题渲染合成一次脚本运行，减少 1,586 这个乘数本身。
3. **热点文件停止"整文件重写 + 整文件读回"（top12 减半 ≈ 省 107 credits，top50 ≈ 202）。** Write 单次平均计费 539,178，是 Edit 的 4.2 倍。做法：DSL/脚本先用离线校验（语法与几何自检）跑通再提交，减少返工；改已有文件一律用 Edit 局部替换；需要复查时 Read 指定行区间而不是全文。`case06_festival.py` 被写读 44 次、`dash.py` 40 次是最直接的改进对象。
4. **用子代理隔离高输出步骤。** 本会话 `subagents.count = 0`（且 `scanned = false`），2,661 次请求的上下文全部单调积累在一条时间线里。把"逐件看图核对、批量渲染、长日志分析"委托给子代理、只回传结论，能同时压低第 1、2、3 项的基数。注意：`scanned = false` 也意味着**若历史上确有子代理运行，其消耗未被本 report.json 计入，8.08 亿是下界**。
5. **精简附件/技能注入（现 82 credits）。** 平均 11,581 token/请求的注入量与当步是否用到该技能无关；长任务中按阶段卸载不用的 MCP/技能比全程挂着更省。
6. **补上真实 usage 采集。** 当前 `tokens` 全部是 `derived`（transcript-ratio 推算），`outputTokens`、`cachedTokens` 为 `unavailable`、`cachedShare = 0` —— 既看不到输出侧成本，也无法确认前缀缓存是否命中。report.json 的 `proxy` 段显示 `enabled = true`、端口 49787，但 `configured = false`、`logExists = false`、`logRecords = 0`、`matched = 0`：监听开关是开的，代理从未真正落盘任何一条 usage 记录，2,661 次请求全部走了 `transcriptRatio` 回退。先把这条链路配置起来，下次分析才能有精确的缓存命中率与单次耗时，而不是给每个请求套同一个推算比例。

若 1–3 同时到位（触发点 45%、Bash 减半、热点文件减半），建模总量约落在 **4.9–5.6 亿 token / 1,300–1,480 credits**，相比本次 2,147 credits 约省三分之一到四成 —— 但这是建模区间，不是可保证的账单数字。

## 数据局限（阅读本报告时必须带上）

| 局限 | 依据 | 影响 |
|---|---|---|
| token 数全部为推算值 | `usageSource = transcript-ratio`、`availability.tokens = "derived"` | 分类/文件级的绝对值有误差，比例结论仍可用；credits 才是实测 |
| 输出 token 与缓存命中缺失 | `availability.outputTokens / cachedTokens = "unavailable"`，`totals` 中为 0 | 0 不等于"确实没有"；无法评估缓存收益，无法核算输出侧成本 |
| 无单次请求耗时 | `proxy.matched = 0`、`logExists = false` | 第九节的时长只能按墙钟陈述，不得当作工作时长 |
| `byTool` 仅覆盖 57.01% | 只含 `tool_use + tool_result` 两类 | 工具占比的分母是总成本，不能与思考/系统项相加 |
| `byFile` 仅覆盖 31.86% | 无法归属到单文件的思考、命令等不在其中 | 文件榜是"可定位部分"的排名，非全量排名 |
| `userContextLimit = 200,000` 为回退默认 | `userContextLimitSource = "default"` | 相关 `peakUserRatio`、danger 建议对本会话无效 |
| 子代理未扫描 | `subagents.scanned = false`、`reason = "no-dir"` | 总量可能低于真实值 |
| 用户轮次仅 7 | `session.turns = 7` | "credits/轮 306.8"这类均摊指标参考意义有限 |
| 30 题 completed 取自题库自身进度 | [`outputs/…/_suite/suite-state.json`](../outputs/2026-10-12T10-04Z-r001/_suite/suite-state.json) | 仅用于计算单题均值，本报告未复核交付质量 |
