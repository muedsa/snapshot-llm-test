# case-02 · 边缘语言 · 取餐牌与会员卡印刷稿

## 场景与受众

- **受众**： fictional 商户「云吞巷」的老板，以及接单的印厂（文盛印务）制版师傅。
- **使用场景**：这是一张要真的送去印厂的对版稿。师傅需要知道成品裁到哪、
  圆角多少毫米、哪条边有色带、哪几孔是模切；老板需要看到四种票券摆在一起
  是什么效果。稿件在 A3 纸上按 90 mm 宽的取餐牌等比放大后阅读。
- **用户要完成的事**：师傅照着「边缘配方」栏切版，不用来回问；老板一眼确认
  「对角切角」和「镜像切角」是两回事。
- **观看环境**：纸面/屏幕上 100% 阅读，最小字号 10 px。

## 内容依据

- 商户名、票号 A-0721 / B-0448、订单明细、会员资料、集章进度、工单号、
  印厂与纸张规格：**全部自拟的演示值**，页脚已注明不代表任何真实订单或授权。
- 两张票面的金额都由**同一份明细求和**得到，不是手写的数字：
  A 牌 `28 + 16 + 12 = 56 元`、B 牌 `32 + 18 + 12 = 62 元`（票面右侧印的是
  行小计，不是单价）。
- 尺寸换算：取餐牌 90×124 mm ↔ 图上 250×346 px；会员卡 85.6×54 mm ↔ 340×214 px；
  集章卡 85×37.5 mm ↔ 340×150 px。比例自洽（会员卡 1.59:1，接近 ISO 7810 的 1.586:1）。

## 视觉选择与探索的能力

主打**圆角 / 单边边框 / 裁剪**家族，先用
`tmp/20261004-182918/B03/probes/probe-c02-edges.png` 九格验证：

| 手法 | 用在哪 | 实测结论 |
|---|---|---|
| `borderRadiusTopLeft` / `BottomRight` 独立取值 | 取餐牌 A（对角切角）、会员卡 | 四角互不影响，探针 A 与 B 的差异就是证明 |
| `borderRadiusTopRight` / `BottomLeft` | 取餐牌 B、集章卡 | 同上，镜像方向也成立 |
| `border` + `borderLeft`（单边色带） | 配方栏「单边色带」 | 单边覆盖统一边框的对应边；**只写一边时其余三边没有边框** |
| `borderTop` + `borderBottom` | 配方栏「上下描边」 | 同上 |
| `ClipOval` | 会员卡头像、10 个集章冲孔 | 椭圆/圆孔的真实裁剪路径（探针 G） |
| `ClipRRect` 四角独立圆角 | 探针 F | 与 `Container` 圆角格式一致 |
| `ClipRect clipBehavior="HARD_EDGE"` | 探针 H | 像素对齐硬边 |
| `ClipRRect borderRadius=200`（>半高） | 探针 I | 自动钳制成胶囊（stadium） |
| `Column crossAxisAlignment="STRETCH"` + `Row SPACE_BETWEEN` | 两张取餐牌的正文 | 票面左名称右金额自动对行 |
| `padding="(18,24)"` | 票面内边距 | EdgeInsets 的两段式（vertical, horizontal） |

### 一个必须写下来的边界

探针 **E** 显示：当同时给 `borderRadius*` 和**单边** `borderLeft` 时，
边框被画成一个**直角矩形**，并没有跟着左侧倒角走（图里黄色边框是方角，
里面才是圆角的深色块）。所以「倒角 + 单边色带」这个组合在 DSL 里做不到
印刷业期待的连续倒角描边；本稿的取餐牌 B 因此改用**渐变底色 + 统一边框**，
把色带做进底色而不是做进边框。这是一个由实测驱动的实现取舍，不是假装实现。

### 另一个诚实的近似

集章卡的「冲孔」用 `ClipOval` + 描边模拟：DSL 没有布尔挖空，
纸色圆盘 + 内圈是行业里最接近的做法，稿面右下角已明确写出这一点。

## 迭代过程（实际看图记录）

1. **v1**：`ClipOval` 只允许一个子节点（我把渐变盘和文字并列了）→ 改成
   `ClipOval > Stack(EXPAND) > [Container, Text]`。
2. **v1**：`borderLeft="14 SOLID"` 少写颜色 → 400 `Failed requirement`；补色。
3. **v2**：票面用 `Stack fit="LOOSE" + alignment` 导致所有非定位子节点叠在
   同一处（LOOSE 下 Stack 收缩到最大子节点，全部按 alignment 重叠）→
   改用 `Column crossAxisAlignment="STRETCH"`，这是正确解法而不是打补丁。
4. **v2**：尺寸线用了绝对坐标，被 `Frame` 又加了一次面板原点 →
   全部改成面板局部坐标；同时修掉 `dim_v` 里把 `Positioned` 塞进
   `Container > Transform` 导致的 `parentData must be StackParentData`。
5. **v3**：票面 Column 内容比可用高度多约 37 px → 收紧 `SizedBox` 间距、
   票号 34→30、padding 24→18。
6. **v4**：底部约 300 px 空白 + 尺寸表被 sheet 的 `Stack` HARD_EDGE 裁掉 →
   调整稿面高度与画布高度；尺寸标注标签按等宽字体的 0.605em 重新计算宽度，
   否则 "250 px = 90 mm" 会被截成 "250 px = 90"。
7. **v5（收尾复审）**：把十张 `final.png` 逐张重新打开后，2.6× 放大两张票面
   （`crops/final-review-c02-cardA.png` / `final-review-c02-cardB.png`）逐行核金额，
   发现 B 牌印「合计 86 元」而三行是 32 + 18 + 12 = 62 元 —— 差 24 元。
   追到 B 牌的合计是写死的字符串，而 A 牌用的是 `sum(items)`，两张票用了两套算法。
   同时 B 牌票面写着「外带 TAKEAWAY / 预计 11 分钟 · 堂食」，可这一格的标题是
   「B · 取餐牌（左侧色带）」、尺寸表也写「取餐牌 B」—— 一张堂食单印在取餐牌的
   样张上。→ 给 B 牌单独一份 `ORDER_B` 明细并用 `sum()` 求和；票面副标题改成
   「取餐牌 PICKUP / 台号 T-07 · 预计 11 分钟」。2.8× 复验
   （`crops/final-review2-c02-total.png`）为 62 元，通过。
8. **v5 顺带排除一处疑似缺陷**：左侧那条竖排「346 px」在 100% 下初看像乱码，
   用 `tmp/20261004-182918/B03/rotcheck.py` 把该区域旋转 −90° 读回后确认
   它就是正常的竖向尺寸标注（自下而上读作 346 px），不是文字错位，故保留。

## 遗留 / 不足

- 单边边框不跟随倒角（见上），这是服务语义限制，无法在 DSL 内修复。
- 集章孔不是真镂空，是视觉近似。
- 票面明细只有 3 行、规格只到「份 / 少冰」这一级，是排版样张而不是收银小票，
  没有做窄宽度下的折行与长菜名截断。
- 稿件按单一比例放大展示，未包含 1:1 出血实样；真实印前文件还需要
  出血框、陷印与总墨量限制，这些都不是本服务能产出的。
